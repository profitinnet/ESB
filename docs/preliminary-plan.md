# Предварительный план интеграционной шины

Статус: предварительный. Это решение для старта разработки, не описание уже настроенного стенда.

Интеграционный слой перевозит события между системами со схемы ландшафта. Платформа MVP — Docker на одном узле Linux. Учётные системы в контейнеры не переносятся.

## Решение

Брокер этапа 1 — Redpanda: Kafka API, встроенный Schema Registry, метрики Prometheus, фактор репликации 1. Простые потоки позже может вести Redpanda Connect. Apache Camel — runtime адаптеров SAP Business One и 1С. Оба пишут в один брокер.

Apache Kafka на хосте уже установлена. В обмен этапа 1 она не входит. Два брокера без общей настройки разведут одни и те же события по разным журналам. Контур Kafka KRaft + Camel остаётся запасным, если политика лицензий потребует брокер только под Apache-2.0.

Сервис наблюдения `ai-ops` от брокера не зависит. Его пишем сами в обоих вариантах.

Отдельный классический MQ рядом с брокером не ставим. Асинхронный обмен идёт через топики. Синхронный вызов Service Layer выполняет адаптер и после ответа системы публикует факт.

## Что уже есть на хосте

На Linux-сервере уже запущены Camel, Kafka и Redpanda. Настройки нет: нет контракта топиков, маршрутов и схем.

Перед первым маршрутом проверяем порты. Kafka и Redpanda по умолчанию слушают 9092. Без явной настройки они либо конфликтуют, либо уже разведены на разные порты. В конфигурации Camel один bootstrap — адрес Redpanda.

Целевой размер хоста для полного MVP: 8 vCPU, 32 ГБ RAM, отдельный SSD от 500 ГБ. Redpanda без Camel укладывается и в 16 ГБ. Пока Camel, Kafka и Redpanda работают вместе, 32 ГБ — рабочая граница, потому что Kafka процесса занимает память, даже если маршруты в неё не пишут.

## Этап 1: четыре эмулятора

Боевые SAP Business One, 1С, EDIN и Вчасно для старта не нужны. Вместо них поднимаем эмуляторы интеграционных контрактов в Docker-сети того же хоста.

Эмулятор повторяет пути, сессию, коды ответов и идентификаторы. Он не ведёт учёт SAP и 1С, не проверяет сертификаты EDIN и не ставит квалифицированную подпись Вчасно. Переход на боевой стенд — другой base URL и секрет при тех же путях и полях.

| Эмулятор | Контракт | Успех маршрута |
| --- | --- | --- |
| SAP Business One | Service Layer: `POST /Login`, создание и чтение заказа, тело ошибки | Camel получает `DocEntry` либо ошибка попадает в DLQ |
| 1С | HTTP-сервис приёма документа, JSON-контракт этого проекта | В ответе номер документа. Повтор того же `id` не создаёт второй документ |
| EDIN | Список новых документов и подтверждение, что документ забран | Событие опубликовано в `doc.edin.received.v1` |
| Вчасно | Создание документа, смена статуса, callback на шину | Статус приходит в `doc.vchasno.status.v1` |

DI API (COM) SAP Business One и COM 1С из Linux-контейнера не вызываем. Integration Suite в MVP не включаем, пока не подтверждено, что он установлен. M.E.Doc в этап 1 не входит.

### Потоки

1. Входящий документ. Эмулятор EDIN → `doc.edin.received.v1` → Camel → `POST` заказа в эмулятор SAP B1 → `erp.order.upserted.v1`.
2. Статус подписи. Эмулятор Вчасно → `doc.vchasno.status.v1` → Camel обновляет документ в эмуляторе SAP B1.
3. Передача в 1С. `erp.order.upserted.v1` → Camel → HTTP-сервис эмулятора 1С.

Этого достаточно, чтобы отладить контракт, идемпотентность, DLQ и трассу. Этого недостаточно, чтобы заменить юридически значимый обмен с EDIN и Вчасно.

## Слои

1. Системы компании остаются снаружи Docker. SAP Business One — действующая система учёта.
2. Адаптеры приводят обмен к каноническому событию. На этапе 1 это Camel. Connect подключаем, когда появится простой HTTP/SQL/файл вне SAP и 1С.
3. Брокер хранит события. Ошибка потребителя уходит в DLQ, исходное сообщение сохраняется.
4. Потребители (домены, DWH, BPM) читают согласованные топики. BPM стоит снаружи брокера.
5. Контур наблюдения читает lag, состояние маршрутов, DLQ и трассы. Учётных данных SAP B1 и 1С у него нет.

Шина перевозит события. Документ с учётной и налоговой силой остаётся в SAP Business One, 1С, EDIN или Вчасно. У мастер-данных один владелец. Остальные контуры получают событие об изменении.

## Контракт сообщения

Имя топика: `domain.entity.action.vN`. Пример: `erp.order.upserted.v1`. Топик ошибок: `dlq.` и имя исходного топика.

Партиций сразу три, чтобы позже добавить потребителей без переименования топика. Фактор репликации 1, пока узел один.

Конверт — CloudEvents 1.0.

| Поле | Пример | Назначение |
| --- | --- | --- |
| `id` | uuid | Ключ идемпотентности потребителя |
| `source` | `sap-b1/orders` | Контур-источник |
| `type` | `com.company.erp.order.upserted` | Тип события |
| `time` | RFC 3339 | Время бизнес-события |
| `subject` | `order-18422` | Ключ партиции, порядок по документу |
| `correlationid` | uuid | Сквозная цепочка между системами |
| `traceparent` | W3C trace context | Поиск трассы |

Схема тела — JSON Schema в Schema Registry Redpanda. Повторная доставка того же `id` не создаёт второй документ в SAP B1 и в 1С.

## Почему брокер этапа 1 — Redpanda

| Критерий | Redpanda + Connect + точечный Camel | Kafka KRaft + Camel |
| --- | --- | --- |
| Ресурсы одного узла | Один процесс брокера, лимит порядка 2 ГБ | JVM, отдельные registry и UI, лимит брокера порядка 6 ГБ |
| Совместимость | Kafka API, Camel-компонент подходит | Родной протокол |
| SAP B1 и 1С | Service Layer закрывает Camel | Camel закрывает и Service Layer, и остальные маршруты |
| Лицензия | Business Source License. Внутренняя шина обычно допустима. Оказание совместимого облачного сервиса третьим лицам лицензия ограничивает. Текст версии сверяем до фиксации | Apache-2.0 |
| Наблюдаемость | Prometheus endpoint и Console в составе поставки | JMX-экспортёр, Apicurio, AKHQ |

Смена Redpanda на Kafka позже меняет брокер, а не контракт событий. Если с первого дня потребуется много сложных маршрутов и лицензия только Apache-2.0, рабочим брокером становится уже стоящая Kafka, а Connect в контур не добавляем.

## Состав Docker

Уже запущены и требуют настройки: Redpanda, Kafka, Camel.

Для этапа 1 добавляем четыре эмулятора. Остальное — по мере сквозного стенда, не всё в первый день.

| Сервис | Роль | Лимит RAM | Когда |
| --- | --- | --- | --- |
| redpanda | Брокер, Kafka API, Schema Registry, метрики | 2 ГБ | Уже стоит, настраиваем |
| camel | Service Layer SAP B1 и HTTP 1С, Quarkus | 1 ГБ | Уже стоит, пишем маршруты |
| kafka | Запасной брокер, в обмен этапа 1 не входит | 6 ГБ | Уже стоит, маршруты не подключаем |
| emulators | SAP B1, 1С, EDIN, Вчасно | 0,5 ГБ на все четыре | Этап 1 |
| console | Топики, группы, схемы | 0,25 ГБ | Вместе с первым потоком |
| postgres | Подтверждения AI и ключи идемпотентности | 0,5 ГБ | Вместе с идемпотентным потребителем |
| prometheus, grafana | Lag, ошибки, диск | 0,75 ГБ | После сквозного стенда |
| loki, alloy | Журналы | 0,75 ГБ | После сквозного стенда |
| otel-collector | Трассы по `traceparent` | 0,25 ГБ | После сквозного стенда |
| ai-ops | Чтение состояния шины, запись после подтверждения | 0,5 ГБ | Когда есть lag и DLQ |
| traefik | TLS-вход | 0,13 ГБ | Когда появятся UI |
| connect | HTTP, SQL, файл, MQTT | 0,5 ГБ | Этап 2, не SAP и не 1С |

Имя проекта Compose — `ibus`. Сеть брокера наружу не публикуем. Снаружи, когда появится вход, только Traefik. Порт 9092 в интернет не открываем.

Диск: 150 ГБ на данные брокера, 80 ГБ на журналы, 20 ГБ на Postgres, остальное — образы и каталог бэкапа.

Лимиты в таблице — потолок контейнера, не замер потребления.

## Порядок работ

| Шаг | Результат |
| --- | --- |
| 1 | Зафиксированы порты. Camel смотрит только в Redpanda. Пробное сообщение записано и прочитано. На хосте 32 ГБ режим `overprovisioned` у Redpanda не включаем |
| 2 | Подняты четыре эмулятора во внутренней сети Docker |
| 3 | Описаны топики этапа 1, JSON Schema, DLQ, конверт |
| 4 | Проходят три потока. Ошибка Service Layer видна в DLQ. Повтор `id` не создаёт второй документ. Трасса сшивается по `correlationid` |
| 5 | `ai-ops` отвечает по lag и составу DLQ и не имеет права на запись |
| 6 | Ночной снимок томов брокера и Postgres. Одна восстановленная копия читает те же сообщения |

Ориентир по календарю одного инженера с ревью архитектора: неделя 1 — порты и эмуляторы; неделя 2 — три потока; неделя 3 — чтение состояния помощником; недели 4–6 — устойчивость тех же потоков; неделя 7 — секреты вне git, проверенное восстановление, описание границы с цехом. Боевой Service Layer эти недели не блокирует.

## Остальные системы

| Контур | Этап | Как подключаем |
| --- | --- | --- |
| SAP Business One, 1С, EDIN, Вчасно | 1 | Эмуляторы, затем смена base URL |
| ECom, WMS и логистика, CRM, SalesWorks | 2 | API или регламентная выгрузка. Протокол Кегельбана заранее не известен |
| BI: DataLake, DWH, OLAP, отчёты, QiVisor | 2 | Потребители согласованных топиков |
| SCADA / ПЛК | 2 | Шлюз на границе цеховой сети публикует агрегаты. Топика команд на ПЛК нет |
| BPM | 2 | Оркестратор снаружи брокера |
| AI Hub | 2 | Потребитель топиков и возможный endpoint модели для `ai-ops` |
| M.E.Doc | 3 | HTTP API или агент на Windows. COM из контейнера недоступен |
| HR и зарплата | 3 | Топиков нет: персональные данные |
| Электронный архив, тендеры, чаты, Office 365 | 3 | После стабильного документного потока |

Чаты могут получить событие «уведомить». Текст переписки в шину не кладём.

## Контур AI

Модель берём из AI Hub или внешнего API. Веса на хост шины не ставим.

Инструменты чтения: consumer group и lag, статус маршрута, просмотр DLQ без полного тела документа, запрос к Prometheus, трасса по `correlationid`.

Инструменты записи после подтверждения человека: пауза и возобновление маршрута, повтор ограниченной пачки из DLQ. Каждое действие пишется в Postgres.

Автоматическая реакция без человека — отдельное решение после MVP и только для паузы маршрута при росте потока DLQ.

## Границы MVP

- Один узел, RF=1. Второй узел и RF=3 — после требования к простою. Kubernetes не используем.
- CDC и Debezium не ставим, пока у системы есть API.
- Команды на ПЛК через шину не идут.
- HR и зарплата в топики не публикуются.
- Учётные данные SAP B1 и 1С сервису `ai-ops` не выдаются.
- M.E.Doc через COM не вызываем.
- SAP Integration Suite обязательным звеном не считаем.

## Открытые решения

| Вопрос | Рабочая гипотеза | На что влияет |
| --- | --- | --- |
| Брокер обмена | Redpanda. Текст BSL сверить до фиксации | Куда смотрит Camel |
| Потоки этапа 1 | EDIN → SAP B1, статус Вчасно → SAP B1, событие B1 → 1С | Первые маршруты |
| Боевая 1С опубликована? | Для эмулятора не важно. Боевую базу включаем отдельно | Момент смены URL |
| Service Layer боевой базы доступен с хоста? | Для старта нет | Только переключение base URL |
| Integration Suite установлен? | Считаем, что нет | Не дублируем публикацию из B1 |
| Модель для `ai-ops` | AI Hub или внешний API | Сеть и секрет endpoint |
| Хост | 8 vCPU, 32 ГБ RAM, 500 ГБ SSD | Лимиты контейнеров |

## Каталог репозитория

Появляется по мере шагов, не целиком в первый коммит:

- `docs/preliminary-plan.md` — этот план;
- `compose/` — описание запуска эмуляторов и того, чего ещё нет на хосте;
- `contracts/` — JSON Schema и примеры конвертов;
- `camel/` — маршруты Service Layer и 1С;
- `emulators/` — SAP B1, 1С, EDIN, Вчасно;
- `ai-ops/` — чтение состояния шины;
- `observability/` — дашборды и сбор метрик.

Теги образов фиксируются в Compose, не в этом плане. Секреты в git не кладём.
